架构总览

设计原则

本方案以四大核心原则为基石，确保系统满足企业级生产环境的严苛要求：

  • 高可用 (High Availability)：多可用区部署、自动故障转移、无单点故障，SLA 目标 99.95%
  • 可扩展 (Scalability)：微服务架构 + 容器编排 + 自动弹性伸缩，支持从 10 人团队到 500+ 用户平滑扩展
  • 安全 (Security)：零信任网络模型、数据加密、身份认证与授权分离、全链路审计
  • 成本优化 (Cost Optimization)：无服务器优先、按需计费、预留实例 + Savings Plans、资源自动回收

系统功能概述

企业知识管理系统涵盖以下核心功能模块，覆盖知识的采集、存储、检索、分析和分发全生命周期：

功能模块描述主要 AWS 服务
统一知识搜索跨文档、消息、链接、知识库文章的全文检索与语义搜索OpenSearch, Kendra
知识图谱实体关系可视化与图遍历查询Neptune
时间线视图实体事件的时间序列展示DynamoDB

基础设施层 (Infrastructure)

VPC 网络设计

采用多可用区 (Multi-AZ) 网络架构，至少部署在 2 个可用区（推荐 3 个），确保任一可用区故障不影响系统整体可用性。网络分为公有子网与私有子网两层：

  • 公有子网：部署 ALB、NAT Gateway、Bastion Host（运维跳板机），面向互联网
  • 私有子网（应用层）：部署 ECS Fargate 任务、Lambda 函数，不直接暴露公网
  • 私有子网（数据层）：部署 RDS、OpenSearch、Neptune、ElastiCache，仅接受应用层访问

负载均衡

使用 Application Load Balancer (ALB) 作为应用层入口，支持基于路径和主机头的路由规则，将请求分发至不同微服务的目标组。ALB 跨 AZ 部署，配合 AWS WAF 实现 Web 应用防护。

容器编排

采用 Amazon ECS Fargate 作为容器运行时平台，免去 EC2 实例管理负担。每个微服务以独立的 ECS Service 运行，配置独立的任务定义 (Task Definition)、自动伸缩策略和健康检查。

  • CPU/Memory 基线分配：按服务负载特征差异化配置
  • Auto Scaling 策略：基于 CPU 利用率（目标 70%）和请求数的复合策略
  • 最小实例数：生产环境每服务至少 2 个任务（跨 AZ），保障高可用

数据层 (Data Layer)

数据层采用 "多库异构" 策略，根据数据特征选择最合适的存储引擎，避免单一数据库成为瓶颈。

Amazon OpenSearch Service — 全文搜索与向量搜索

替代原有内存搜索方案，OpenSearch 同时支持传统 BM25 全文检索和 k-NN 向量搜索，实现关键词搜索与语义搜索的融合（Hybrid Search）。

  • 索引设计：按数据类型分索引 — documents、messages、links、kb_articles
  • 向量字段：每条记录存储 1536 维嵌入向量（由 Bedrock Titan Embedding 生成）
  • 集群配置：3 个专用主节点 + 数据节点跨 2 AZ，启用 UltraWarm 节点用于冷数据
  • 分词器：集成 IK 中文分词插件，支持自定义行业词典

Amazon Neptune — 知识图谱

Neptune 是完全托管的图数据库，用于存储和查询实体间关系。支持 Apache TinkerPop Gremlin 和 SPARQL 两种查询语言。

  • 数据模型：属性图 (Property Graph)，节点类型包括 Person、Company、Project、Document、Topic
  • 关系类型：WORKS_ON、AUTHORED、MENTIONS、RELATES_TO、BELONGS_TO 等
  • 查询场景：N 度关系发现、最短路径、社区检测、实体关联推荐
  • 部署：Multi-AZ，1 主 + 1 只读副本

Amazon RDS (PostgreSQL) — 结构化数据

用于存储用户、项目、客户、元数据等结构化数据。PostgreSQL 选型基于其强大的 JSON 支持和扩展生态。

  • Multi-AZ 部署，自动故障转移
  • 只读副本用于报表查询分流
  • 启用 Performance Insights 监控慢查询

Amazon S3 — 文档存储

  • 存储桶设计：raw-documents（原始上传）、processed-documents（解析后文本）、embeddings-cache
  • 生命周期策略：90 天后转 S3 IA，365 天后转 Glacier
  • 版本控制 + 服务端加密 (SSE-KMS)

Amazon DynamoDB — 会话与时间线

  • 对话历史表：PK=user_id, SK=session_id#timestamp
  • 时间线事件表：PK=entity_id, SK=event_timestamp
  • 按需容量模式 (On-Demand)，自动适应突发流量
  • TTL 自动清理过期会话（30 天）

Amazon ElastiCache (Redis) — 缓存层

  • 缓存热门搜索结果、用户 Session、图谱高频查询结果
  • Cluster 模式，跨 AZ 副本
  • TTL 策略：搜索缓存 5 分钟，Session 30 分钟，图谱缓存 15 分钟

4

AI/ML 层 (Intelligence Layer)

AI/ML 层是系统的智能核心，负责语义理解、内容生成、实体识别和智能检索。全部采用 AWS 托管 AI 服务，无需自建模型训练基础设施。

Amazon Bedrock — 大语言模型

Bedrock 提供多种基础模型的统一 API 访问，本方案主要使用以下模型：

用途推荐模型说明
AI 对话 / 问答Claude 3.5 Sonnet高质量中文理解与生成，支持长上下文
报告生成Claude 3.5 Sonnet结构化输出能力强，支持 Markdown/HTML 模板
关键词解释Claude 3 Haiku轻量级模型，响应快、成本低
文本嵌入Titan Embedding V21536 维向量，中英文兼顾

Amazon Bedrock Knowledge Bases — RAG 管道

Bedrock Knowledge Bases 提供开箱即用的 RAG（检索增强生成）管道，将企业文档转化为可被 LLM 检索引用的知识源。

  • 数据源：S3 中的处理后文档（PDF、Word、HTML、TXT）
  • 分块策略：固定 300 token + 20% 重叠，保持语义连贯性
  • 向量存储：OpenSearch Serverless（Bedrock KB 托管）或指向自建 OpenSearch 集群
  • 检索方式：Hybrid Search（语义 + 关键词），Top-K = 5，相关度阈值过滤

Amazon Kendra — 企业搜索

Kendra 作为补充搜索引擎，提供自然语言查询理解和精确答案提取。其预置连接器可直接对接 SharePoint、Confluence 等数据源，减少自研连接器工作量。

Amazon Comprehend — 自然语言处理

用于文档的自动实体识别和关键词提取，是知识图谱自动构建的核心组件。

  • 实体识别 (NER)：自动识别人名、公司、日期、地点、事件
  • 关键短语提取：提取文档核心概念作为图谱节点属性
  • 自定义实体识别：训练自定义模型识别行业特定实体（如项目编号、产品型号）
  • 情感分析：用于客户反馈和舆情文档的情感标注

数据接入与处理管道 (Data Ingestion Pipeline)

数据接入层是知识管理系统的 "血液循环系统"，负责从多个异构数据源持续采集、清洗、处理和索引数据。设计上采用事件驱动架构，确保松耦合和高可扩展性。

核心组件

  • Amazon EventBridge：事件总线，所有数据源变更事件通过 EventBridge 路由到对应处理管道
  • AWS Step Functions：编排多步骤文档处理工作流（提取 → NER → 索引 → 图谱），支持错误重试和人工审核
  • AWS Lambda：无服务器处理函数，按需触发，处理完即释放资源
  • Amazon SQS：缓冲队列，削峰填谷，防止下游服务过载

安全架构 (Security)

安全设计遵循 "纵深防御" 原则，从网络边界、身份认证、数据加密到审计日志，构建多层安全屏障。

身份认证与授权

  • Amazon Cognito：用户池管理，支持用户名密码、企业 SAML SSO、钉钉 OAuth 等多种登录方式
  • JWT Token：Cognito 签发 ID Token 和 Access Token，API Gateway 验证后转发至后端
  • RBAC：基于角色的权限控制 — 管理员、编辑者、查看者，角色信息存储于 RDS
  • 文档级访问控制：每个文档关联可见性标签（公开/团队/私有），搜索时通过 OpenSearch 过滤器实现权限过滤

网络安全

  • 安全组 (Security Groups)：最小权限原则，应用层仅允许 ALB 入站，数据层仅允许应用子网入站
  • 网络 ACL：子网级别的额外防护，拒绝非预期端口
  • VPC Endpoints：S3、DynamoDB、Bedrock 等服务通过 VPC 终端节点访问，流量不出 VPC
  • AWS WAF：部署于 ALB 和 API Gateway，防护 SQL 注入、XSS、恶意爬虫、DDoS

数据加密

场景加密方式密钥管理
S3 存储SSE-KMS (AES-256)AWS KMS CMK，自动轮换
RDS 存储TDE (透明数据加密)KMS CMK
OpenSearch 存储节点级加密KMS CMK
DynamoDB 存储SSE-KMSKMS CMK
传输中数据TLS 1.2+ACM 托管证书
Redis 传输TLS + AUTH TokenSecrets Manager

审计与合规

  • AWS CloudTrail：记录所有 API 调用，日志存储至 S3 + CloudWatch Logs
  • S3 访问日志：记录文档桶的所有读写操作
  • 应用审计日志：记录用户搜索行为、文档访问、权限变更，存储至 DynamoDB
  • IAM 策略：每个 ECS 任务使用独立的 Task Role，遵循最小权限原则

高可用与容灾 (HA & DR)

系统设计目标为 RTO ≤ 15 分钟、RPO ≤ 5 分钟，通过 Multi-AZ 部署和自动化故障转移机制实现。

各服务高可用配置

备份策略

  • RDS：自动快照每日一次，保留 14 天；PITR（时间点恢复）保留 7 天
  • OpenSearch：自动快照每小时一次，存储至 S3，保留 14 天
  • Neptune：自动快照每日，保留 7 天；支持手动快照长期保留
  • DynamoDB：PITR 启用，连续备份保留 35 天
  • S3：版本控制启用，可选跨区域复制 (CRR) 至灾备区域

Route 53 健康检查

配置 Route 53 健康检查，监控 ALB 端点和各服务 /health 接口。当主区域不可用时，可通过 DNS Failover 切换至灾备区域（如启用多区域部署）。

灾备等级建议

  • 基础方案（推荐）：单区域 Multi-AZ，RTO 15 分钟，月成本基线
  • 增强方案：Pilot Light — 灾备区域仅运行最小数据同步，紧急时启动应用层，RTO 1-2 小时，额外成本约 20%
  • 高级方案：Warm Standby — 灾备区域运行缩小版环境，RTO 5-10 分钟，额外成本约 50%

告警策略

  • P0 (紧急)：服务不可用 > 2 分钟、API 错误率 > 5%、RDS CPU > 90% → SNS 通知 + PagerDuty
  • P1 (重要)：搜索延迟 P95 > 2s、LLM 超时率 > 10%、队列堆积 > 1000 → SNS 通知
  • P2 (一般)：磁盘使用率 > 80%、缓存命中率 < 60% → 邮件通知

  • AI 服务面板：Bedrock Token 用量与成本、RAG 检索延迟、对话并发数

  • 业务指标面板：日活跃用户、搜索次数、文档上传量、知识图谱节点增长

二次开发架构 (Extensibility for Secondary Development)

二次开发能力是本架构的核心竞争力。通过插件化、API 优先、事件驱动三大机制，确保客户和合作伙伴能在不修改核心代码的前提下扩展系统功能。

插件架构 — 数据源连接器 SDK

连接器采用标准接口设计，开发者只需实现 ConnectorInterface 即可接入新数据源：

# Python Connector SDK 接口定义
from abc import ABC, abstractmethod
from typing import List, Dict, Any

class ConnectorInterface(ABC):
    """数据源连接器标准接口"""

    @abstractmethod
    def authenticate(self, credentials: Dict[str, str]) -> bool:
        """验证数据源连接凭据"""
        pass

    @abstractmethod
    def list_resources(self, path: str = "/") -> List[Dict[str, Any]]:
        """列出数据源中的资源（文件、页面等）"""
        pass

    @abstractmethod
    def fetch_content(self, resource_id: str) -> Dict[str, Any]:
        """获取单个资源的完整内容"""
        pass

    @abstractmethod
    def get_changes_since(self, since_timestamp: str) -> List[Dict[str, Any]]:
        """增量同步：获取指定时间后的变更"""
        pass

    @abstractmethod
    def get_metadata(self) -> Dict[str, Any]:
        """返回连接器元数据（名称、版本、支持的功能）"""
        pass

API 优先设计

  • OpenAPI 3.0 规范：所有 API 以 OpenAPI Spec 定义，自动生成文档和客户端 SDK
  • 版本管理：URL 路径版本 (/v1/, /v2/)，旧版本至少维护 12 个月
  • 向后兼容：新增字段不破坏旧客户端，废弃字段标注 deprecated 后保留 2 个版本周期
  • 分页与过滤：统一使用游标分页 (cursor)，支持 OData 风格过滤表达式

  • 向量搜索 (Hybrid Search)
  • 时间线视图 (DynamoDB)
  • 缓存层 (Redis) 接入

Phase 3 — 高级功能 (第 13-16 周)

  • 报告生成助手
  • 新员工入职关键词探索
  • 高级图谱分析（社区检测、路径发现）
  • Kendra 企业搜索集成
  • 前端插件系统 (Module Federation)
  • 连接器 SDK 发布

Phase 4 — 优化与扩展 (持续)

  • 性能优化与负载测试
  • 更多数据源连接器
  • Python / Node.js SDK 开源

  • 成本优化（预留实例、Spot、生命周期策略）
